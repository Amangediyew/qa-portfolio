# Тест-план: веб-приложение Swag Labs (SauceDemo)

| Поле | Значение |
|---|---|
| Объект тестирования | https://www.saucedemo.com (интернет-магазин Swag Labs, учебное приложение) |
| Автор | Амангельдыев Эзиз |
| Версия документа | 1.0 |
| Тип тестирования | Ручное: функциональное, регрессионное, UI/UX, негативное |

## 1. Введение
Документ описывает подход к тестированию основных пользовательских сценариев интернет-магазина Swag Labs: авторизация, каталог, корзина, оформление заказа, меню.

## 2. Цели тестирования
- Убедиться, что основные пользовательские сценарии работают по ожиданиям.
- Проверить валидацию полей и сообщения об ошибках.
- Выявить дефекты интерфейса и логики, особенно для пользователей с особым поведением (`problem_user`, `error_user`, `visual_user`, `performance_glitch_user`).
- Подготовить набор тест-кейсов и чек-листов для повторного (регрессионного) прогона.

## 3. Область тестирования

### В области (in scope)
| Модуль | Что проверяем |
|---|---|
| Авторизация | Вход, выход, ошибки валидации, заблокированный пользователь, прямой доступ по URL без входа |
| Каталог товаров | Отображение, сортировка, карточка товара, кнопки Add to cart / Remove |
| Корзина | Добавление, удаление, счётчик, сохранение после перезагрузки, переход к оформлению |
| Оформление заказа | Форма данных, валидация, итоговая сумма и налог, завершение заказа |
| Боковое меню | All Items, About, Logout, Reset App State |
| UI / кроссбраузерность | Вёрстка, иконки, изображения, адаптивность |

### Вне области (out of scope)
- Нагрузочное и performance-тестирование (отдельный проект).
- Безопасность (пентест), автотесты.
- Реальные платежи (в приложении их нет).

## 4. Тестовые данные
Пароль для всех пользователей: `secret_sauce`

| Логин | Назначение |
|---|---|
| `standard_user` | Базовый сценарий |
| `locked_out_user` | Проверка заблокированного пользователя |
| `problem_user` | Пользователь с проблемами UI и логики |
| `performance_glitch_user` | Медленные ответы |

| `visual_user` | Визуальные расхождения |

## 5. Подход и техники тест-дизайна
- Эквивалентное разбиение и анализ граничных значений (поля формы).
- Позитивные и негативные сценарии.
- Таблица решений для авторизации.
- Исследовательское тестирование (exploratory) после выполнения тест-кейсов.

## 7. Критерии начала и окончания тестирования
**Вход:** сайт доступен, тестовые учётные записи работают, подготовлены тест-кейсы.

**Выход:**
- выполнено 100% тест-кейсов приоритета High и не менее 90% остальных;
- все дефекты Blocker/Critical задокументированы;
- итоговый отчёт составлен (см. `docs/05-test-summary-report.md`).

## 8. Классификация дефектов
| Severity | Описание |
|---|---|
| Blocker | Приложение/функция недоступны, обходного пути нет |
| Critical | Ломается ключевой сценарий (вход, заказ) |
| Major | Функция работает неверно, есть обходной путь |
| Minor | Небольшая неточность, не влияющая на сценарий |
| Trivial | Косметика (опечатка, выравнивание) |

| Priority | Описание |
|---|---|
| High | Исправить в первую очередь |
| Medium | Исправить в плановом порядке |
| Low | Исправить при наличии времени |

## 9. Риски
| Риск | Митигация |
|---|---|
| Сайт учебный, поведение может измениться без предупреждения | Фиксировать дату прогона и скриншоты |
| Нет доступа к коду и серверной части | Тестирование методом чёрного ящика |
| Часть багов зависит от типа пользователя | Тестировать под всеми тестовыми учётками |
